### W-001 🔴 CRITICAL — Lock file compiled for Python 3.13; runtime image is Python 3.11

**File:line:** `worker/requirements.lock:4`

```
# This file is autogenerated by pip-compile with Python 3.13
```

The runner stage is `FROM python:3.11-slim` (`worker/Dockerfile:14`), but
`requirements.lock` was compiled under Python 3.13 (`pip-compile --output-file=...`).
Wheel selection is ABI-dependent: `psycopg2-binary`, `greenlet`, `grpcio`, `cffi`,
`caio`, and all Temporal protobuf bindings carry `cp313`/`cp311` ABI tags. On Ubuntu
24 (Kernel 6.x) the installer silently falls back to sdist builds for any wheel whose
`cp313` tag has no `cp311` counterpart, potentially selecting different transitive
versions than tested.

Additionally, `google-cloud-aiplatform>=1.60.0` is declared in
`worker/requirements.txt:17` (required by `agents/runtime/providers/vertex_provider.py`)
but is **absent from `requirements.lock`** — it was not resolved during the 3.13
`pip-compile` run. On Ubuntu 24 / GCP this matters directly because Vertex AI
auth uses Application Default Credentials, which are the natural credential source on
GCE instances.

**Fix:**
1. Pin builder and runner to the same Python minor version that produced the lock —
   either bump both stages to `python:3.13-slim` or recompile the lock against 3.11.
2. Run `pip-compile` with `--python-version 3.11` (or the chosen target) on CI and
   gate merges on a clean re-lock.
3. Add `google-cloud-aiplatform` back to the lockfile and pin it.

### W-002 🔴 CRITICAL — `_bmad-output/` write path is NOT the mounted volume; artifacts are ephemeral

**Files:** `_bmad/bmm/config.yaml:7`, `_bmad/config.toml:21-22`, `docker-compose.yml:156-157`

The BMAD runtime resolves `output_folder` to
`{project-root}/_bmad-output` → `/app/_bmad-output` inside the container (via
`agents/runtime/bmad_loader.py:260` using `HELIX_PROJECT_ROOT=/app`).

The compose volume mount is:

```yaml
volumes:
  - helix_artifacts:/app/data/artifacts   # docker-compose.yml:157
```

`/app/data/artifacts` is a completely different path from `/app/_bmad-output`.
`planning_artifacts` resolves to `/app/_bmad-output/planning-artifacts` and
`implementation_artifacts` to `/app/_bmad-output/implementation-artifacts`. Both
are written to the container's writable layer — they vanish on container restart,
crash, or image replacement. On GCP's e2-medium (ephemeral local disk), a worker
crash mid-workflow loses every artifact written by completed activity steps.

This also breaks the backend's artifact-content API
(`/api/v1/agent-workflows/{id}/artifact-content`), which assumes artifacts are
readable from `helix_artifacts` alongside the backend container.

**Fix (choose one):**
- Remap the compose volume to `-  helix_artifacts:/app/_bmad-output` and update
  the backend's `HELIX_PROJECT_ROOT` mount to match, OR
- Set `output_folder = "{project-root}/data/artifacts/_bmad-output"` in
  `_bmad/custom/config.toml` so BMAD writes into the already-mounted volume.
- Document the chosen canonical path and add a healthcheck assertion that
  `planning_artifacts` is writable at startup.

### W-003 🟠 HIGH — `max_concurrent_activities` not set; default 100 thrashes a 3+2 DB pool

**Files:** `worker/main.py:66-86`, `worker/db/session.py:28-33`,
`docs/review-v3/REVIEW_PERFORMANCE.md` (H-9)

`Worker(client, task_queue=..., workflows=[...], activities=[...])` passes no
`max_concurrent_activities` argument. The Temporal Python SDK default is 100. The
worker DB pool is `pool_size=3, max_overflow=2` (5 total). Each `persist_workflow_step_activity` and each cost-write in `bmad_executor` opens a `SessionLocal()` connection.

On a GCP e2-medium (2 vCPU, 4 GB RAM), accepting 100 simultaneous activities means
up to 100 OS threads competing for 5 DB connections — 95 block on checkout. The
Temporal task-slot budget is exhausted while activities wait on DB.

**Fix:**
```python
worker = Worker(
    client,
    task_queue=TASK_QUEUE,
    max_concurrent_activities=int(os.getenv("WORKER_MAX_CONCURRENT_ACTIVITIES", "10")),
    max_concurrent_workflow_tasks=int(os.getenv("WORKER_MAX_CONCURRENT_WORKFLOWS", "5")),
    workflows=[...],
    activities=[...],
)
```
Size the worker DB pool to match: `pool_size = max_concurrent_activities`. For an
e2-medium running 1–2 parallel BMAD plans, 5–10 activities concurrent with a 10-conn
pool is appropriate. Expose both via env so GCP operators can tune without rebuilding.

### W-004 🟠 HIGH — Healthcheck opens a real Temporal TLS connection every 30 s (INFRA-017)

**Files:** `worker/Dockerfile:40-43`, `docs/review-v2/REVIEW_INFRA.md` (INFRA-017)

```dockerfile
HEALTHCHECK --interval=30s --timeout=10s --start-period=30s --retries=3 \
    CMD python -c "import asyncio, os; from temporalio.client import Client; \
asyncio.run(Client.connect(os.getenv('TEMPORAL_ADDRESS', 'localhost:7233')))" \
    || exit 1
```

Every probe:
1. Spawns a new Python interpreter (cold import of `temporalio` + gRPC stack).
2. Performs a full TLS handshake and gRPC connect.
3. Tears everything down.

On Ubuntu 24 with GCP's inter-region Temporal (cross-AZ), the gRPC handshake
alone can take 80–200 ms. At 100 ops/min the worker spawns 2 Python processes/min
purely for health probes. The `start_period` of 30 s is shorter than the typical
cold-boot time for this image (imports LangGraph + PydanticAI + all LLM SDKs;
measured >30 s on e2-medium; see INFRA-005 in v2 review). This causes the
container to report `unhealthy` on a healthy slow-boot and trigger spurious restarts.

**Fix — lightweight liveness probe:**
```dockerfile
HEALTHCHECK --interval=30s --timeout=5s --start-period=60s --retries=3 \
    CMD python -c "import worker.main" || exit 1
```
This confirms the entrypoint is importable (catches broken env, missing deps) without
creating a network connection. Add a separate readiness signal at the application
level if Temporal reachability must be checked (log a WARN on startup if connect
fails, let Docker see liveness separately from Temporal health).

### W-005 🟠 HIGH — Heartbeat emitted only at monolithic activity END, not during LLM call

**Files:** `worker/activities/bmad_activities.py:48-49`

```python
result = run_bmad_graph(...)           # blocking — can take 10–15 min
if activity.in_activity():
    activity.heartbeat("bmad_graph_completed")
```

The heartbeat is sent **after** `run_bmad_graph` returns. If `run_bmad_graph` takes
longer than Temporal's `heartbeat_timeout` (default 10 min; configurable per activity),
Temporal marks the activity as dead and retries. The per-node activities in
`bmad_node_activities.py` do heartbeat correctly via `_run_with_heartbeats` every
10 s. The monolithic `execute_bmad_graph_activity` does not — it calls the same
opaque `run_bmad_graph` wrapper that chains all 13 nodes internally without any
Temporal heartbeat.

**Fix:** Apply the same `_run_with_heartbeats` pattern used in `bmad_node_activities.py`
to `execute_bmad_graph_activity`. The monolithic graph blocks for 10–15 min on large
projects; wrap it:

```python
@activity.defn
def execute_bmad_graph_activity(input_data: dict[str, Any]) -> dict[str, Any]:
    from worker.activities.bmad_node_activities import _run_with_heartbeats
    result = _run_with_heartbeats(
        lambda: run_bmad_graph(...),
        detail_prefix="bmad_graph",
    )
    return result
```

### W-006 🟠 HIGH — No `.dockerignore` inside `worker/`; root `.dockerignore` excludes `backend/tests` but not `backend/alembic/versions/*.py` test fixtures or large optional dirs

**Files:** `.dockerignore:1-60`

There is no `worker/.dockerignore`. The single root `.dockerignore` is used for
build context (correct for the repo-root build context in `docker-compose.build.yml`).
Verified exclusions are good: `__pycache__`, `.git`, `frontend/.next`, `backend/tests`,
`_bmad-output`, most of `agents/bmad/BMAD-METHOD/` (docs, test, website, tools, evals).

However the following are NOT excluded and add unnecessary size to the worker image:

| Path | Approx. size | Used by worker? |
|---|---|---|
| `agents/bmad/BMAD-METHOD/src/tools/` | ~2 MB JS | No |
| `agents/tests/` | — | No (excluded from worker context) |
| `backend/alembic/` | — | No — worker must NOT run migrations |
| `website/` | ~4 MB | No |

The `backend/alembic/` directory is the most important: including it in the worker
image tempts future operators to run `alembic upgrade head` from the worker
container. It serves no worker function.

**Fix:** Add to `.dockerignore`:
```
website/
agents/tests/
backend/alembic/
# already excluded: agents/bmad/BMAD-METHOD/tools (add if missing)
agents/bmad/BMAD-METHOD/tools
```

### W-007 🟡 MED — SIGTERM not explicitly handled; `worker.run()` relies on asyncio default

**Files:** `worker/main.py:92`, `docker-compose.yml:148`

`await worker.run()` blocks until the Temporal SDK receives a shutdown signal. The
Temporal Python SDK does register `SIGTERM` internally, but this works correctly only
when Python is PID 1 AND has no intervening shell. The `CMD` in `worker/Dockerfile:45`
is exec-form (`CMD ["python", "-m", "worker.main"]`), which is correct — Python
is PID 1 in the runner container and SIGTERM is forwarded directly. No `init: true`
is set in `docker-compose.yml` for the worker (`docker-compose.yml:145-163`).

The risk: if any future change switches to shell-form CMD (e.g. to wrap with an env
sourcing script), SIGTERM will go to `/bin/sh`, not Python, and in-flight activities
will be killed mid-LLM call.

**Fix:** Add `init: true` to the worker service in `docker-compose.yml` (consistent
with the recommendation in INFRA-008):

```yaml
worker:
  init: true
```

This ensures tini forwards SIGTERM correctly regardless of CMD form changes.
Also: document in `DEPLOY.md` that the Temporal worker's graceful drain window is
`temporalio.worker.Worker`'s default (the SDK waits for in-flight activities to
complete up to `graceful_shutdown_timeout`, which defaults to 0 — immediate). For
LLM activities that take >60 s, set:

```python
worker = Worker(..., graceful_shutdown_timeout=timedelta(minutes=15))
```

### W-008 🟡 MED — Worker logs use plain `logging.basicConfig`; no JSON format, no correlation_id

**Files:** `worker/main.py:97-100`

```python
logging.basicConfig(
    level=os.getenv("LOG_LEVEL", "INFO"),
    format="%(asctime)s %(levelname)s %(name)s %(message)s",
)
```

The backend uses `pythonjsonlogger.JsonFormatter` with `ts`/`level`/`logger` fields
(`backend/app/core/logging_config.py:14-17`). Worker logs are plain text. On GCP
Cloud Logging, text lines from the worker are stored as unstructured `textPayload`
while backend logs arrive as structured JSON with `ts`, `level`, `logger`. A
`correlation_id` is passed through `bmad_node_activities.py:66` (`input_data.get("correlation_id")`) to the executor but never injected into the logger context — it only
appears if the executor explicitly logs it.

**Fix:**
1. Extract `configure_logging()` from `backend/app/core/logging_config.py` into a
   shared `helix_common/logging.py` package (or copy the 15-line function to
   `worker/logging_config.py`).
2. Call `configure_logging(APP_ENV)` at the top of `worker/main.py` before the first
   log statement.
3. In `_execute()` / `_run_with_heartbeats()`, inject `correlation_id` into a
   `logging.LoggerAdapter` so every log line from activities carries the request trace.

### W-009 🟡 MED — `persist_workflow_step_activity` imports from `app.models.workflow` (backend package coupling)

**Files:** `worker/activities/bmad_node_activities.py:353`

```python
from app.models.workflow import WorkflowStep
```

The `PYTHONPATH` in the worker image includes `/app/backend` (`worker/Dockerfile:21`)
specifically to allow this import. This is an explicit design choice (comment at
`worker/Dockerfile:20`) but has several consequences:

- Any change to `app.models.workflow` (e.g. a new required column added in a backend
  migration) can break the worker without a worker rebuild if the images drift.
- The worker image therefore transitively depends on the entire backend models tree.
- On GCP, if backend and worker images are built separately and one is updated without
  the other, schema mismatch is silent until a `persist_workflow_step_activity` fails.

The `worker/db/session.py` module correctly uses its own `SessionLocal` and avoids
`app.db.session`, but model coupling remains.

**Fix:** Move `WorkflowStep` (or a minimal `WorkerWorkflowStep` dataclass) to a
shared `helix_models` package importable by both images, or duplicate the model
definition in `worker/db/models.py` and pin both to the alembic migration version.
At minimum, add a CI check that builds both images together and runs a smoke import.

### W-010 🟡 MED — `start_period: 30s` is too short for cold-boot on e2-medium

**Files:** `worker/Dockerfile:40`

```dockerfile
HEALTHCHECK --interval=30s --timeout=10s --start-period=30s --retries=3
```

The worker imports, on first boot: `temporalio`, `langgraph`, `pydantic-ai`,
`anthropic`, `openai`, `boto3`, `google-cloud-aiplatform` (once fixed), `grpcio`,
`sqlalchemy`, plus the backend models tree. On a GCP e2-medium (2 vCPU, shared,
memory-constrained), cold Python startup for this dependency set exceeds 30 s
regularly — especially after a `docker pull` when the page cache is cold.

`start_period` expiring before the worker is ready causes Docker to count the first
failing health probe toward `retries: 3` and trigger a restart, which makes the image
loop-restart on first deploy.

**Fix:** Increase `start_period` to `60s` (or `90s` for large e2-medium with cold
disk). This is consistent with the INFRA-005 recommendation in the v2 infra review.

### W-011 🔵 LOW — Shared `python:3.11-slim` base with backend; no multi-stage deduplication across Dockerfiles

**Files:** `worker/Dockerfile:1,14`, `backend/Dockerfile:1,17`

Both Dockerfiles independently resolve and install from separate lockfiles. They share:
- The same `python:3.11-slim` base image (good — single layer in cache).
- Identical `agents/`, `connectors/`, `_bmad/` COPY blocks.

The worker installs a superset of backend's dependencies (adds `temporalio`, `langgraph`,
`pydantic-ai`, all LLM provider SDKs). There is no shared builder stage; both pay full
install cost independently on CI.

On GCP Cloud Build, two separate `docker build` runs each pull Python base + install
all deps. A shared monorepo build with `--target runner_worker` / `--target runner_backend`
would halve CI time for the deps common to both.

This is LOW because it does not affect runtime behavior, only CI cost and image size
consistency. No change is required for the GCP deploy to work.

### W-012 🔵 LOW — `requirements.lock` includes `pywin32` (Windows-only); will fail on Ubuntu 24

**Files:** `worker/requirements.lock:409-412`

```
pywin32==311
    # via mcp
pywin32-ctypes==0.2.3
    # via keyring
```

`pywin32` is a Windows-only wheel. It is listed in the lockfile because
`pip-compile` was run on Windows (Python 3.13, Windows). On Ubuntu 24, `pip install
-r requirements.lock` will either:
- Skip it silently (if pip finds no compatible wheel, falls back to skipping on
  environment-marker mismatch), or
- Fail with `No matching distribution` if the lock entry lacks environment markers.

This is a direct consequence of the Python 3.13/Windows `pip-compile` environment
mismatch flagged in W-001. Fixing W-001 (re-lock from a Linux/3.11 environment)
will also correct this entry.

### W-013 🔵 LOW — No `HEALTHCHECK` watchdog for artifact store writability

**Files:** `worker/Dockerfile:40-43`, `_bmad/bmm/config.yaml:7`

The current healthcheck only verifies Temporal connectivity. It does not verify that
`/app/_bmad-output/planning-artifacts` (or the configured `planning_artifacts` path)
is writable. If the compose volume fails to mount (e.g. volume name mismatch on GCP
when `COMPOSE_PROJECT_NAME` changes — see INFRA-033 in v2 review), the worker will
pass the healthcheck, accept tasks from Temporal, and fail every activity with a
filesystem write error. The failure surfaces only in activity error logs, not in
container health status.

**Fix:** Add a filesystem probe to the healthcheck (or a separate startup probe):
```dockerfile
HEALTHCHECK --interval=30s --timeout=5s --start-period=60s --retries=3 \
    CMD python -c "
import os, pathlib
p = pathlib.Path(os.getenv('HELIX_PROJECT_ROOT', '/app')) / '_bmad-output' / 'planning-artifacts'
p.mkdir(parents=True, exist_ok=True)
(p / '.healthcheck').touch()
" || exit 1
```

### W-014 🔵 LOW — No restart policy verification that covers in-flight Temporal activities

**Files:** `docker-compose.yml:148`

```yaml
restart: unless-stopped
```

`unless-stopped` is correct for the GCP deploy — it restarts on crash and on Docker
daemon restart, but not after a manual `docker stop`. The Temporal SDK's graceful
shutdown (noted in W-007) drains in-flight activities before exit. However,
`graceful_shutdown_timeout` defaults to `0` (no drain), meaning a crash or OOM kill
will abandon any in-flight LLM call. Temporal will retry the activity on the next
worker boot (correct behavior), but retrying a 90-second Anthropic Opus call wastes
quota and adds latency.

**Fix:** Set `graceful_shutdown_timeout=timedelta(minutes=15)` in the worker
constructor (W-007 fix covers this) and document in `DEPLOY.md` that the e2-medium
should have at least 1 GB free memory headroom for the worker to avoid OOM kills
mid-activity.

## Worker does NOT run Alembic — confirmed

`worker/main.py` contains zero references to `alembic`, `upgrade`, or
`create_all`. The worker entry point connects to Temporal and starts listening;
it does not touch schema migrations. The only DB interaction is the `persist_workflow_step_activity` upsert via `worker/db/session.py`. Confirmed safe.

The `backend/Dockerfile:42` runs `alembic upgrade head` on every backend boot
(a separate concern tracked as INFRA-015 in the v2 review). The worker image does
include `backend/alembic/` in its build context (see W-006 for the recommendation
to exclude it), but no code path inside the worker imports or invokes Alembic.

## Verdict

**Two CRITICAL blockers before GCP deploy:**

1. **W-001** — lockfile compiled on Python 3.13/Windows; runner is 3.11/Linux.
   `google-cloud-aiplatform` is absent from the lock despite being in `requirements.txt`.
   On GCP (e2-medium, Ubuntu 24), the install is non-deterministic and Vertex AI
   auth will fail silently.

2. **W-002** — BMAD artifacts write to `/app/_bmad-output` (container writable layer)
   but the compose volume mounts at `/app/data/artifacts`. Every artifact produced by
   a completed activity step is lost on container restart or redeployment.

**Four HIGH issues** must be resolved before production load:

- W-003: activity concurrency unbounded vs. a 5-connection DB pool.
- W-004: healthcheck cold-starts a TLS session every 30 s; `start_period` too short
  for e2-medium cold boot (also INFRA-017 from v2 review).
- W-005: monolithic `execute_bmad_graph_activity` sends no heartbeat during the
  10–15 min graph run; will be killed by Temporal's heartbeat timeout on long plans.
- W-006: `backend/alembic/` and large BMAD auxiliary directories included in image
  unnecessarily; `pywin32` lock pollution (related to W-012).

The **MED/LOW items** (W-007 through W-014) are GCP-hardening hygiene: structured
logs, `init: true`, graceful drain timeout, and the backend-model coupling —
none will cause an immediate outage but all will surface as operational pain within
the first week of real traffic.
